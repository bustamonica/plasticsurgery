# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.

## Repo layout and branches

- The GitHub default branch is `claude/breast-augmentation-ai-preview-56w494` (the Next.js app + training track).
  `origin/main` is an unrelated legacy Python project; never base work on it or push to it.
- `app/`, `components/`, `lib/` are a Next.js preview-studio app; `training/` is the custom-model training track (data pipeline + ai-toolkit config). See `HANDOFF.md` and `training/README.md`.
- Website checks: `npm test` (Node's built-in runner over `**/*.test.ts` - there is no jest/vitest here) and `npx tsc --noEmit`. `npm test` runs Node's runner straight over `.ts` sources, so it needs Node >= 22.18 for unflagged type stripping (`engines` in `package.json` pins that floor, and tests import source files with an explicit `.ts` extension). `npm run lint` is inert: no ESLint config is committed, so `next lint` only offers to create one. Training-track tests are separate (pytest, below).

## CI

- `.github/workflows/ci.yml` runs on `pull_request` and pushes to the default branch: a `web` job (`npm ci`, `next build`, `tsc --noEmit`, `npm test` on Node 22.18) and a `training` job (`pip install` + `pytest` for `training/`). The ESLint job is a commented-out TODO slot pending `ba-viz-eslint-setup`.

## Training track sharp edges

- Authoritative docs: `training/README.md` (pipeline, RunPod steps) and `training/dataset_schema.json` (consent contract per pair).
- Never commit photos or datasets: `training/data/` is gitignored on purpose; the consented clinic corpus lives outside the repo at `~/firstmate/data/clinic-corpus/` (scraper intake in `<clinic>/raw/`, with `.scraper-cache/` beside it).
- **A pair only counts once it is in the FINISHED tree**, `clinic-corpus/<clinic>/<pair-id>/`. `<clinic>/staging/` and `<clinic>/raw/` are unfinished and invisible to every corpus walk, dataset build and audit - drdanielbarrett, drkolker and sanantonio held 745 pairs in staging and nothing finished until 2026-08-15, and corpus totals quoted anywhere older than that blend the two trees. `training/scripts/emit_corpus.py` is the carry-through (staging -> finished) and the only thing that should write that tree: it re-encodes nothing (`ingest.py` already stripped EXIF, and it refuses rather than strips if an image still carries any), never overwrites an existing pair, and `--report` enumerates every staged pair with its disposition. Always `--dry-run` first. Presence in the finished tree is what makes a pair count, and a documented exclusion does not unmake that: several clinics are ruled out in prose while their pairs sit live in that tree (`training/clinic_watermarks.md`, "Excluded on paper vs excluded in fact").
- Withheld pairs are **retired, not deleted**: `training/retired_pairs.json` enumerates every id kept out of the finished corpus with its ruling and reason (currently the captain's 176 retired laterality labels of 2026-08-15 - 134 sanantonio, 42 drdanielbarrett - plus `sanantonio-24007-oblique-right` withheld as contested, plus the 119 heavenly pairs retired under `retired_watermark` on the captain's 2026-08-15 on-body-watermark ruling). It is an enumeration and not a rule on purpose: a rule is a live query over staging, and a re-annotation would silently widen a ruling made over a fixed set. `emit_corpus.py` copies each withheld pair into `~/firstmate/data/ba-viz-emit-backlog/quarantine/<reason>/<clinic>/<pair-id>/` and leaves `staging/` untouched; that tree's `MANIFEST.md` is the per-pair record. The registry is the sole authority on a retirement and is keyed by pair id, not by clinic, so `--clinic` cannot be misspelled into letting a retired pair through, and deleting an id from the registry is sufficient to re-emit that pair. The registry gates the EMIT PATH only: an entry keeps a pair from being carried out of `staging/` and does nothing about one already in the finished tree, so removing an already-emitted pair takes a change to the corpus tree itself - do not assume a registry edit is enough. `--clinic` selects which staged pairs are carried as well as which corpus subdirectory they land in: `ingest.py` stages every clinic into one flat tree, so a staged pair belonging to another clinic is reported as `other-clinic` and left for that clinic's own run rather than misfiled under this one.
- Which clinic burns what into its photos, and whether it touches breast tissue, is `training/clinic_watermarks.md` - the roll-up the per-clinic scout reports kept re-deriving and losing. The standing captain ruling (2026-08-15) is that a mark clear of breast tissue is acceptable unmasked; one drawn across the breasts rules the clinic out. A documented exclusion is only *intent* until something on disk enforces it - that file's "Excluded on paper vs excluded in fact" says which exclusions actually hold. **heavenly is the worked example of the gap and of closing it**: it sat "excluded on paper" with all 119 pairs live in the finished tree (no registry entry, no quarantine hold) for weeks, until the captain ruled 2026-08-15 to discard the clinic outright and it was retired 2026-08-16 (`training/retired_pairs.json`'s `retired_watermark` section, pairs moved into `~/firstmate/data/ba-viz-emit-backlog/quarantine/retired-watermark/heavenly/`) - a *registry entry alone would not have done this*, since it gates the staging->finished emit path and does nothing to a pair already emitted; the fix was moving the files. wny's `wny-after-only-watermark` question is now closed too (2026-08-19), by a different mechanism: see the one-sided-watermark bullet below.
- Gallery intake: `training/scripts/scrape_gallery.py` (pluggable `CLINICS` configs; 35 clinics as of the 2026-08-15 batch - see the module docstring and per-parser docstrings for each gallery's markup contract). View laterality / unlabeled views come from a visual-annotation JSON (see the scraper docstring); `training/scripts/annotate_contact_sheets.py` renders the review sheets. Undocumented spec fields are omitted or the schema's `unknown` enum - never invented. Before assessing or scoping a new clinic gallery, load the `clinic-prospecting` skill (`.claude/skills/clinic-prospecting/SKILL.md`).
- sanantonio (BRAG book plugin) sharp edges: images are side-by-side before|after composites split at the horizontal midpoint (`split_composite_image`); the WordPress URL slug (not the BRAG `data-case-id`) is the unique case key; Height/Weight have no documented units (kept verbatim in notes); Natrelle Inspira model numbers (e.g. 'SRM-445') encode cc but are NOT decoded, per the drkolker 'Mini Motiva' precedent - a decoder is a captain-level decision.
- **A watermark on ONE half of a pair and not the other is a label leak, and is CROPPED** (captain, 2026-08-19; `.claude/skills/clinic-prospecting/SKILL.md` Screen 4a is the full lesson). An edit model asked to enlarge the breasts can satisfy that by adding or removing the mark, and every quality gate the pipeline has passes it - it surfaces only as a model that learned nothing. Found on four clinics by averaging every frame per half and high-passing the average (bodies cancel, a fixed-position mark survives): tccs on the BEFORE half (743 pairs), roth, camp and wny on the AFTER half (162/299/10). `ClinicConfig.bottom_crop_px` trims BOTH halves equally at emit - tccs 130, roth 175, camp 110, wny 60, each measured per clinic and confirmed constant in pixels rather than as a fraction of height. Never transfer one clinic's crop to another, never mask instead (a mask preserves the leak), and exclude what drops below the 400px floor rather than shipping it shrunken (cost: 85 pairs). Screen for it at INTAKE by comparing before-half against after-half mark incidence; tccs reached the finished corpus twice before anyone compared the halves.
- Gallery platform families (2026-08 batch of 20 more consented clinics; one parser per family, reused across clinics on the same builder): Influx legacy numbered-subpage (drkolker, lakeshore/marina via the shared `influx_swiper` kind, austinweston, charlotte, allure), Etna Interactive composite (drrohrich's 2x2 grid, wny's per-view 2-up), Webflow (sixsurgery structured fields, skplastic's 2x3 grid), Studio 3 Marketing/DatoCMS paginated (drgrover, basu, drteitelbaum - strip the `?w=` query string for the bare original), and one bespoke WordPress parser per remaining clinic (harrington, drjeremyhunt, drmiroshnik, privateclinic, mitchellbrown, heavenly, mya, drtavakoli). `crop_grid_cell()` handles multi-panel grid composites (front/oblique/side x before/after in one file) via `ImagePair.grid_shape`/`before_cell`/`after_cell`; `resolve_view()` also accepts a `view_hint` that is already a full schema view (e.g. heavenly's older filenames spell out 'Left-Oblique').
- The `etna` kind (2026-08-15 batch of 12 more consented clinics: tccs, camp, colville, roth, kochcarlisle, wmips, southeastern, northraleigh, ablavsky, hasen, curtsinger, coastal) is one parser configured twelve times for the Etna Interactive gallery. Photos are side-by-side before|after composites at `//images.<host>/content/images/<procedure>-<case>-<view>-detail.jpg`. Two things are read off that filename and neither is guessable: the leading slug is the case's OWN procedure and is the purity screen (curtsinger case 159 sits in the breast-augmentation gallery and publishes as `mommy-makeover-159-...`), and the view token is either positional (`view-1`, documents nothing) or named (`left-oblique`, documents view AND laterality - a page-documented source like heavenly's). Read the positional order per CASE, never per clinic: northraleigh runs front/oblique/side, wmips runs front/SIDE/oblique, and colville case 19 publishes no front at all. Five `.case-description` layouts are handled and pinned by `etna_*` fixtures - including northraleigh's chart with NO delimiter between fields (`Approach: InframammaryPlacement: Subfascial...`), which is why `ETNA_LABEL_RE` also allows a label to start at a lowercase-to-uppercase transition. A pose is not a view: `front-arms-raised`/`bent-forward` are deliberately not folded into `front`.
- **Etna galleries cannot be fully enumerated.** A category page renders 12 cases into HTML and serves the rest only through `admin-ajax.php` under `/wp-admin/`, which every one of these robots.txt files disallows. The prev/next case chain (seeded from the listing AND from every sibling category listing, because the chain is a set of disconnected components) reached the declared total on 7 of 12 clinics and plateaued on the rest - 556 of 1299 published cases overall. Sitemaps carry zero gallery case URLs, `/page/2/`, `?pg=`, `?page=` and `?start=` all 404, and the listing's filter form is client-side. Do not re-derive this; the fix is an ask to the practice or to Etna Interactive, not more crawling. `etna_declared_total()` reads the gallery's own `EII_GALLERY_JS ... "state":{"total":N}` so every run reports its own shortfall.
- One clinic's `patient-details` block is not one markup. The shared `influx_swiper` template (lakeshore, marina) publishes the same spec block three ways on the same site - one `<p>` per `Label: value`, one `<li>` per field inside a single wrapper `<p>`, and a bare-value layout that drops the labels and prints each value alone - and the whole block also appears once more as the text of the wrapper `<p>` that parents the real ones. `influx_swiper_parse_case` therefore reads innermost `<p>`/`<li>` only, scans each line for known labels (`INFLUX_FIELD_LABELS`) instead of splitting at the first `": "`, and classifies a label-less line by content. Assume any new gallery does the same before trusting a single-layout parser; all three layouts are pinned by the `lakeshore_case_*` fixtures in `training/tests/test_scrape_gallery.py` (a single-layout parser silently cost 57 cases / 218 pairs here).
- Chart metadata (`placement`, `incision`, `height_cm`, `weight_kg` on `CaseSpecs`) comes from CHART text only, never the clinic's narrative, and only `influx_swiper` and `etna` populate it so far (etna reads it off labelled chart fields like northraleigh's `Placement:`/`Approach:` and roth's `Placement:`/`Incision:`). A narrative that names an incision may be explaining the options rather than reporting this patient's (marina case 7463 walks through dual-plane *and* subglandular), and a published range is not a measurement (sixsurgery's `100 - 149 lbs`, which is why `height_to_cm`/`pounds_to_kg` convert a single documented figure or return `None`).
- Before changing a parser that more than one clinic shares, prove the blast radius: re-parse every cached case for every clinic offline (`PoliteFetcher(cache, offline=True)` + `collect_cases` + `build_meta`, no images) on the base revision and on yours, then diff the rebuilt metas per clinic and per field. `ba-viz-emit-backlog/report.md` section 3.5 is the precedent; `ba-viz-emit-lakeshore/report.md` section 4 is a worked example of what a silent parser miss costs. Three clinics (drkolker, drdanielbarrett, sanantonio) have no cached listing page, so an offline re-parse covers 20 of 23.
- Visual annotation is genuinely expensive at this corpus's scale (3000+ pairs across the 2026-08 batch have no page-documented view): treat it as a distinct, bounded pass per clinic via `annotate_contact_sheets.py` (`--side both` renders each pair's before|after adjacent; `--min-dim 400` drops pairs `ingest.py` would reject anyway), not something to rush or guess through.
- Annotate `front` first and separately: front/oblique/side is a reliable call at 12 pairs per contact sheet, and front is the view most cases publish. Laterality is NOT reliable that way - measured against heavenly's filename-documented labels, blind left/right calls from contact sheets scored ~5/9, with a strong bias toward answering "left". So laterality needs the AGENTS.md landmark rule, and the landmark has to be anchored: the case's own front view fixes the absolute frame (in a front view the patient's left is on the viewer's right), then a mark visible in both the front and the oblique/side tells you which side faces the camera. Without such a mark, leave the pair unannotated - a wrong guess is worse than a missing pair in medical training data.
- The corpus convention for laterality (derived from heavenly's `Left-Oblique`/`Right-Oblique` filenames, the only page-documented source): `oblique-left`/`side-left` means the patient's LEFT side faces the camera, which in frame puts the near shoulder/arm on the VIEWER'S RIGHT with the body angled toward the viewer's left. Note that heavenly's per-case labels separate the two groups only as a population (mean body-mass centroid 0.555 vs 0.473 of frame width) and are not independently verifiable case by case, so treat them as the convention's definition rather than as per-case ground truth.
- `ingest.py`'s 400px floor, not annotation, is the binding constraint for several 2026-08 clinics: privateclinic publishes 0 of 77 spec-documented pairs at >= 400px (median 305 after the composite split), marina 20 of 219 (median 288), harrington 50 of 92, mitchellbrown 5 of 15. Check viability with `--min-dim 400` before spending an annotation pass.
- sixsurgery publishes every photo with opaque circles censoring the nipples. The pairs validate fine but training on them would teach the artifact, so they are deliberately not emitted pending a captain ruling; since the censorship gate landed, `ingest.py` also rejects them on its own (97 of 117 cached images).
- `training/scripts/censorship.py` rejects censored/annotated images at ingest (opaque sticker circles and bars, blur bands, mosaic, saturated ink annotations). It is anchored on a skin silhouette, so backdrop watermarks are kept by design. Measured 0.34% false rejects on the corpus (6 of 1782), all drdanielbarrett webp exports so retouched that patches of torso carry no texture at all - if a clean-looking pair is rejected as "texture-free patch of skin", that is the known case, not a new bug. Re-measure with the recipe in the module docstring before touching a threshold. A second false-positive family shows up on corpus-wide re-scans and is worth knowing before running one: a dark backdrop sliver between two body parts (armpit/inner-arm gaps) merged into the skin silhouette, a white divider strip in a stacked-panel composite, or smooth/soft-focus limb skin reading as texture-free. `austinweston-01-front` is not one of those - it carries a genuine skin-tone patch over the groin/underwear in both before and after, present in the clinic's own published source and predating this pipeline, left as-is pending a captain call.
- `training/scripts/deidentify.py` runs NO face detection or blurring, by captain ruling 2026-08-14: the consented clinics contractually guarantee no faces appear in what they publish, which is stronger than anything the code could check. Do not reintroduce a detector, and in particular do not reintroduce a rule that decides by where a blur sits in the frame - position cannot separate a face from a shoulder (`ba-viz-emit-drdanielbarrett/report.md` section 5.2). Every Haar detection ever recorded on this corpus was a false positive (a breast in profile, a shoulder, a hip, hair), and the blur destroyed clean pairs at ten clinics before removal; all but one were recovered 2026-08-15. `deidentify.py`'s module docstring owns the loss detail and `~/firstmate/data/ba-viz-emit-backlog/quarantine/MANIFEST.md` the per-pair disposition - read them there rather than re-deriving counts from the older scout reports. The one pair still outstanding is `heavenly-case23-front`, named here because a pointer cannot reference a key that does not exist: its pair key was never recorded and cannot be derived from the case's two published filenames (`27250527-LACA.jpg` and `27250527-LACA-1.jpg`, neither carrying a view), so it needs a fresh visual view call belonging to the separate view audit.
- The quarantine tree mixes **live holds with superseded audit-trail artifacts**, so membership by pair id is a conservative gate, not a statement that the pair is bad. The `deidentify-blur-damage/` copies for drmiroshnik, drdanielbarrett, marina and wny are SUPERSEDED - the clean re-derived pairs are live under the same ids - and the manifest says so, but nothing in the directory layout does. Measured on the 5 drdanielbarrett pairs: Laplacian variance inside the recorded Haar box is ~1 in the quarantine copy and 15-693 in the staged one, and the pair's undamaged half matches to within re-encode noise. `emit_corpus.py` still holds anything present in that tree - with one exception, the retirement subdirectories listed in its `QUARANTINE_DIRS`, where `retired_pairs.json` is the authority and the tree copy is only an archive of it. Three of those it writes itself (`retired-laterality/`, `withheld-contested/`, `retired-watermark/`); the other two (`retired-watermark-staging-dup/`, `retired-watermark-corpus-staging-dup/`, the 2026-08-16 hand-move of 63 heavenly ids out of the two root-level duplicate-ingest dumps) it never writes and is listed only so they are read as archives - a bucket left out of that list holds unconditionally and would put its pairs beyond the registry edit meant to undo the ruling. Heavenly's `retired-watermark/heavenly/` copies are therefore held by the registry entry, not by their presence in the tree. So the hold still costs those 5 pairs; they are the cheapest recovery available and need only a captain nod plus a `superseded/` split of the tree.
- As of 2026-08-15 what `deidentify.py` still does is strip EXIF/GPS, by re-encoding the images it writes (`encode_stripped()`); `ingest.py` re-encodes as well. That is not theoretical: 36 of 5656 corpus images carry EXIF, and `harrington-177-front` carries camera make/model (Canon EOS Rebel T6) and 2020 capture timestamps. 14 of the 36 are in pipeline trees rather than raw intake, i.e. they predate the pipeline running over them.
- Corpus images are not uniformly `.jpg`: `~/firstmate/data/clinic-corpus/<clinic>/<pair>/{before,after}.*` mixes `.jpg` (majority), `.jpeg` (mya), `.png`, and `.webp` (drdanielbarrett). Any corpus-wide scan must glob `before.*`/`after.*`, not hardcode `.jpg`, or it silently skips whole clinics.
- **Not every top-level directory in the corpus root is a clinic, and the non-clinic ones are dangerous.** `clinic-corpus/_staging/` is a pre-emit leftover (2026-08-12, predating `emit_corpus.py`) holding 308 pair folders: 245 duplicate live finished pairs, and 63 are heavenly - pairs the captain retired, still sitting there after the retirement emptied `clinic-corpus/heavenly/`. A naive `*/*/meta.json` walk therefore re-admits a retired clinic and double-counts a tenth of the corpus. Skip any top-level entry starting with `_` or `.` (also `.scraper-cache/`) and say what you skipped; `find_pair_folders()` in `build_dataset.py` does this and prints the count. Any corpus total that does not exclude it is inflated - the finished tree is 2142 pairs, not the 2569 a raw walk reports.
- The finished corpus is the honest source for a dataset build, not `data/clean`: only the corpus tree has the `retired_pairs.json` retirements actually applied. `build_dataset.py` therefore accepts either layout (flat `<pair>/`, or clinic-partitioned `<clinic>/<pair>/`). It splits train/val **by patient, not by pair** - one patient publishes up to five views, so a per-pair split puts the same person in both halves and the val sample grid, the only evidence a run produces, gets scored on a patient the model memorised. It also re-encodes every image on the way out rather than copying bytes: the corpus still contains EXIF-bearing images (14 reached a build before this was added, carrying Photoshop tags and 2024-2025 capture timestamps), and this is the last stage before the images leave the machine for a rented pod.
- 240 finished pairs carry no `volume_cc` and cannot produce a caption - 237 of them are the whole of drteitelbaum, which publishes no volumes. They are skipped with a reason, so the trainable corpus is 1902 of 2142. Coverage of the three caption axes as of 2026-08-16: view front 995 / side-left 300 / oblique-left 292 / side-right 169 / oblique-right 146 (right-facing views have about half the examples of left-facing); profile NOT RECORDED 1072 / high 321 / moderate 277 / moderate-plus 226 / **extra-high 6** (from only 4 patients, and only 2 of those lateral - treat extra-high as untrained, and note this is why the `unbacked` configurator gate on it still holds); volume 140-700 cc over 125 distinct values, but the only long contiguous run of well-populated 10 cc buckets is 250-389, so granularity claims outside roughly 230-490 cc are not supported by the data.
- mitchellbrown's gallery page lives on `drmitchellbrown.com` but canonicalizes (redirect) to `torontoplasticsurgery.com`, which also hosts all its images; `ClinicConfig.base_url` points at the canonical host directly. That host had one multi-hour outage window during the 2026-08 scrape (TCP connection refused, recovered on its own) - unrelated to the scraper.
- `ingest.py` `MIN_DIMENSION` is 400 (not 512) by captain ruling: drkolker publishes ~75% of cases at 418px; those pairs need ~2.5x upscale to 1024px training res.
- Tests: `cd training && python -m pytest tests -q` (deps in `training/requirements.txt`).
- The consented corpus is 35 clinics as of 2026-08-15. `~/firstmate/data/report/` is a presentation COPY (README.md + samples.html + one folder per clinic); `clinic-corpus/` stays authoritative. When adding a batch, count what `ingest.py` ACCEPTED, never the scraper's intake tree, and say which tree each number came from - conflating the two is how three clinics reported healthy numbers for weeks that were never real.
- `training/configs/qwen_edit_lora.yaml` is validated against ai-toolkit commit `6d8afa5684000b69db97cc40504a972a85615e3b`; the toolkit renames keys often, so re-diff its example config before using a newer commit.
- Caption parity is a hard contract: `build_caption()` in `training/scripts/build_dataset.py` and `buildCustomModelPrompt()` in `lib/prompt.ts` must emit byte-identical instruction text. Update both (and their shared vocabulary in `lib/implants.ts`) together. It is now enforced from both sides rather than by convention: `training/caption_parity_cases.json` holds the golden captions and neither language owns it - `training/tests/test_captions.py` asserts the Python side, `lib/prompt.test.ts` the TypeScript side. Add a case there when the format changes. Only a subset of `dataset_schema.json` reaches a caption; the chart/frame fields (`placement`, `incision`, `height_cm`, `weight_kg`, `bra_size_before`, `chest_width_cm`) are curation/eval metadata and `tests/test_schema.py` asserts they never leak into one.
- A caption is a training LABEL, so an unrecorded field is omitted, never defaulted. The caption states the three axes the product exposes - exact `volume_cc` (never bucketed or rounded; 10 cc granularity at inference depends on the literal figure), `profile`, and `view` - and drops any clause whose field the clinic did not record. Before 2026-08-16 `profile` defaulted to "a balanced profile" on the 61% of pairs carrying none, which taught the model that an unrecorded outcome was a moderate one, and `view` reached no caption at all, which is why the model could not be asked for a projection. `lib/prompt.ts` must omit on the same rule; a caller that knows the photo's view should pass it, since every training caption carries one.
- `lib/prompt.ts` imports `./implants.ts` with the explicit extension and splits type-only bindings into `import type`. Node's test runner resolves ESM specifiers verbatim and only strips types, so without both, `lib/prompt.test.ts` cannot load the module (`tsconfig.json` sets `allowImportingTsExtensions` for exactly this).
- The website's AI provider seam is `AI_PROVIDER` in `.env.example`; `gemini` is the default and the Gemini prompt in `lib/prompt.ts` (`buildEditPrompt`) is intentionally different from the training-caption format.
- Configurator options the corpus doesn't yet back are gated behind an `unbacked` flag on their `lib/implants.ts` entry (currently extra-high profile, teardrop shape) and hidden by default; flip `NEXT_PUBLIC_ENABLE_UNBACKED_IMPLANT_OPTIONS` (`.env.example`) to show them. Read it via `availableProfiles()`/`availableShapes()`, not `PROFILES`/`SHAPES` directly, in any code that renders or validates selectable options - that keeps the UI (`app/studio/page.tsx`) and the API gate (`app/api/generate/route.ts`) consistent. There is no shared `lib/config.ts`; env vars are read ad hoc at their point of use. Flipping the flag needs no code change, but it does need a rebuild and redeploy to take effect (both for the studio bundle and the `/api/generate` gate): Next.js inlines `NEXT_PUBLIC_*` values into the build output rather than reading them from the running process, unlike `GEMINI_API_KEY`, which is genuinely read at runtime server-side in `app/api/generate/route.ts`.
